# 为什么由消息队列安排对话执行

[English](README.md) | [文档入口](../../README-zh.md)

用户点击发送, 只是 Session 获得新输入的一种方式. 子代理和后台命令会完成, Goal 可能还需要继续, 用户也可能在 Agent 执行或手动压缩时补充要求. 我们希望这些输入能有一致的交付顺序, 用户不必等到会话空闲才有地方提交.

## 为什么空闲时也先入队

如果只有一次用户输入, 收到后直接启动 Turn 很直观. 但不同来源分别启动, 就需要各自判断 Session 是否忙碌, 此刻该执行哪件事, 以及启动失败后输入应该留在哪里. 相近时间到来的输入还可能各自认为应该开始新一轮.

我们选择统一先安排交付, 包括 Session 空闲时的普通发送. 队列决定什么时候交付内容, Turn 负责实际执行这一轮. 这样不必在每个输入来源重复处理同一套启动选择.

代价是多了一段排队状态和相应的界面反馈. 用户看到发送成功时, 不能把它理解为模型已经读到, 或消息已经正式保存. 队列也不保证每个排队项都单独启动一个 Turn, 等待中的多条用户输入可以一起交付.

## 为什么区分排队与立即引导

用户有时只是安排下一件事, 有时是在纠正当前正在做的事. 如果所有新输入都立即进入当前执行, 下一件事可能干扰尚未完成的任务; 如果全部等待下一轮, 用户的纠正又可能来得太晚.

因此普通排队输入留给后续 Turn, 用户也可以主动选择立即引导. 引导等当前完整一批工具调用处理结束后交付, 不强行打断一个已经开始的工具动作.

这个选择接受了引导不能立即生效的限制. 对已经执行的点击, 命令或写入, 新要求不会自动撤销其结果. 交付时机需要让用户看得出来, 不能仅因为点击过立即引导, 就假装它已经被当前模型请求采用.

## 为什么领取还不算正式保存

一条输入可能已经被选中交给某个 Turn, 但准备模型或保存消息仍然可能失败. 如果领取时就把它当成正式历史删除, 用户可能失去尚未处理的内容.

我们选择在消息保存成功后再确认消费. 停止或失败时, 未正式保存的用户输入退回草稿, 已保存的消息留在历史中. 这也避免了失败后自动重试可能再次产生模型费用或重复执行操作.

界面因此需要区分等待, 已领取和已保存. 用户不能随时删除或再次引导已经被领取的内容, 拒绝操作时需要解释原因. 我们接受这部分状态复杂度, 用来保留输入的实际去向.

## 当前保留的限制

当前队列只存在于进程内存, 不承担应用重启后的自动恢复. 我们没有把所有待交付通知和草稿都变成另一套持久任务系统. 代价是尚未正式保存的输入不能被当作已经持久保存的历史.

输入调度的用法和具体顺序见 [Turn 模块](../../../src/turn/README-zh.md). 如果用户明确需要可靠的重启恢复, 再针对未交付输入的保存, 取消和重放规则重新讨论.
