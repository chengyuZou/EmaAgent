# 为什么集中判断工具权限

[English](README.md) | [文档入口](../../README-zh.md)

我们需要让用户知道某次工具操作会做什么, 以及批准后究竟允许了多大范围. 文件, 命令, 网页和电脑操控的操作信息不同, 但用户规则, 会话批准和权限模式不适合在每个 Tool 内重复实现.

## 为什么保留 checkPermissions, 又集中作决定

Tool 最清楚自己的实际操作: 要读写哪个路径, 执行什么命令, 或是否需要启动电脑操控. 因此保留 checkPermissions 提供这些信息.

最终放行, 拒绝或询问则交给 Permission. 如果 Tool 各自解释规则和批准, 同一个会话选择可能在不同工具中得到不同含义, 新增工具也容易再复制一套权限逻辑.

我们接受 Permission 需要按操作类型解释不同条件, 不为了统一而把文件路径, 命令和网络目标都当成没有意义的输入字符串. Tool 提供事实, 不再负责一套小型 Permission.

## 为什么程序判断与用户回答分开

程序可以判断允许执行, 禁止执行, 或需要询问用户. 用户只在需要询问时选择允许本次, 按说明范围允许本会话, 或拒绝本次. 程序要求询问不等于用户已经作出选择.

我们保留这两种不同含义, 让批准和拒绝的实际来源说得清楚. 代价是需要两个数据表达, 但避免把一个程序判断结果误认为用户授权, 或把用户按钮直接当成完整判断流程.

## 为什么不替任意输入生成批准范围

同一个工具名有时足够表达批准范围, 例如允许本会话后续申请启动电脑操控. 对文件, 目录或命令, 工具名又可能太宽.

我们选择由实际操作提供可以记住的范围和可读说明. 不能解释复用范围时, 就只允许或拒绝本次, 不根据任意输入自动猜一条会话批准.

这需要更多分类判断, 也可能让某些操作重复询问. 我们接受这部分交互成本, 不用一个含糊的本会话允许按钮暗中扩大批准范围.

## 为什么批准仍不覆盖所有限制

明确拒绝优先于允许, 已批准一段电脑操控也不等于批准同轮的 Shell 或 MCP. 绕过普通权限询问的模式仍然保留明确询问规则和必要确认.

这减少了模式和批准之间的歧义, 代价是选择绕过模式后仍可能看到确认. 我们要求界面解释这次为什么询问, 不把模式名称当成所有请求都必然放行的保证.

会话批准只在当前进程保留, 不承诺退出应用后继续有效. 具体范围, 判断顺序和用法见 [Permission 模块](../../../src/permission/README-zh.md).
