# 为什么这样设计电脑操控

[English](README.md) | [文档入口](../../README-zh.md)

EmaAgent 操作的是用户正在使用的电脑. 用户仍然可以点击和输入, Agent 也可能在同一时间操作. 我们需要让用户能够随时收回操控, 同时避免 Agent 根据已经变化的画面继续执行旧动作.

## 为什么取消自动暂停

暂停方案原本希望保留当前任务: 检测到用户操作后停下来, 用户处理完自己的事情, 再点击继续. 对需要临时修改文档的场景, 这个想法很直观.

但真实键鼠输入并不总意味着用户想接管任务. 用户可能只是处理另一个工具的权限弹窗. 如果这些操作都触发暂停, 处理完弹窗后还要再恢复电脑操控, 一次正常交互就多了一步. 暂停还要求同时协调排队动作, Turn 的等待和恢复时机. 点击继续也不能证明原来的窗口, 光标和内容仍然适合执行旧动作.

因此我们选择取消输入触发的暂停. 用户修改目标窗口后, 让旧观察失效. 尚未执行的旧动作返回未执行; 已经执行一部分的动作如实报告中断情况. 模型重新观察, 再决定下一步. 恢复一段旧动作序列不再是默认行为.

这个选择减少了用户反复点击继续的负担, 也省去了为暂停恢复维护一套等待状态. 代价是用户与 Agent 同时操作同一窗口时, 观察可能反复失效, 需要更多模型请求和截图, 任务也可能变慢. 我们接受重新观察的成本, 不把用户的继续操作视为旧画面仍然有效的证明.

## 为什么操控只存在于一个 Turn 内

允许跨 Turn 保留操控可以减少重新启动的步骤, 但用户看到一轮对话已经结束时, 很难判断 Agent 是否仍然持有电脑操控能力. 如果任务失败或停止后提示条还在, 这个边界会更加模糊.

我们选择让任务执行与操控的结束边界一致: Turn 完成, 失败或取消时, 都先结束所属电脑操控, 再报告本轮已经结束. 下一轮需要操作电脑时重新启动. 本会话批准可以减少再次申请权限的交互, 操控本身仍随 Turn 结束.

## 为什么结束操控不等于停止对话

用户可能只是想收回键鼠, 仍然需要 Agent 汇报已经完成什么, 解释阻碍, 或继续处理其他工作. 因此 Esc, 提示条结束按钮和 ComputerEnd 只结束电脑操控. 聊天里的停止生成才取消整个 Turn.

结束后, 已排队的旧电脑动作不能在重新启动时恢复执行. 否则用户以为已经收回控制, Agent 却可能继续完成先前的点击或输入. 我们接受之后可能需要重新观察和规划, 换取结束操作的含义明确.

## 为什么只允许一个主 Agent 操作

桌面只有一套当前焦点和键鼠位置. 两个 Agent 各自认为正确的操作, 放在一起可能变成向另一个窗口输入或点击错误位置. 我们选择限制同时操控的主 Agent 数量, 子代理不能独立争用这套输入.

这限制了电脑操作的并行程度, 但让用户能够明确知道谁正在使用电脑. 用户与 Agent 共用桌面的冲突仍然存在, 重新观察也不能保证模型每次都判断正确; 这套取舍没有把桌面变成隔离的自动化环境.
