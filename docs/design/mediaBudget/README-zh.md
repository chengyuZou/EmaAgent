# 为什么所有来源的媒体共用发送预算

[English](README.md) | [文档入口](../../README-zh.md)

模型上下文不仅受 Token 容量影响. 多张图片等媒体积累后, 实际请求体也可能很大, 即使文字尚未达到上下文上限, 请求仍可能无法发送.

## 为什么不只限制电脑截图

曾考虑只保留最近几张电脑观察图. 但任务需要的前文可能主要就是这些图片, 单独采用很小的保留数量会过早丢掉证据. 普通附件也同样可能积累, 只处理电脑截图没有控制整次请求的问题.

我们选择让附件, 电脑观察和其他工具结果中的图片遵守同一规则. 数量和编码体积共同约束要发给模型的媒体, 而不是按来源各保留一套固定数量. 可发送的音频和文件也计入同一媒体预算.

代价是不同来源之间会竞争预算. 统一规则不代表每个任务所需的旧画面都能继续保留, 但不需要猜测某种来源就应当更早被删除.

## 为什么处理发送副本

我们希望减小编码体积, 又保留本地素材和历史. 因此处理要发出的副本, 不修改 SQL 中的原消息或磁盘原图.

不透明 PNG 尝试更小的 JPEG 编码, 透明图片保留 PNG. 只采用更小的结果, 不改变这里发送副本的宽高. 尤其电脑操作需要使用画面坐标, 随意缩放会让观察和点击位置更难保持一致.

我们接受有损编码可能影响细小文字, 透明图即使重新编码也可能很大. 压缩只能减少体积, 不能阻止媒体不断积累, 所以仍需要总预算.

## 为什么超限时从旧媒体开始省略

我们选择优先保留较新的完整媒体项, 较早内容超限后用明确的说明代替. 不截断 base64, 也不为被省略的图片编造描述. 消息位置和工具调用配对仍然保留.

最新一项本身就超过体积预算时, 明确报错, 让用户减小附件或调整参数. 静默省略唯一的新图片, 可能让模型在没有看到它时继续回答.

代价是长时间画面对比可能失去较早的直接视觉依据. 原媒体仍在本地历史或附件中, 能否再次读取取决于已有引用和可用工具, 不能认为模型会自动补回全部内容.

## 当前预算不保证什么

这些参数限制的是本次发送的媒体数量与编码体积, 包括 base64 增大的部分, 不是供应商整个 HTTP 请求的上限. URL 只计算本次发送的地址, 也不能据此预知服务端读取远端内容的体积.

我们选择先统一处理本地能够确定的内容. 模型或网关仍可有额外限制, HTTP 请求体过大与 Token 上下文超限也需要分别报告. 当前默认值及具体转换见 [Context 模块](../../../src/context/README-zh.md).
