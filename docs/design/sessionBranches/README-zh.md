# 为什么暂时放弃 Session 内的历史分支

[English](README.md) | [文档入口](../../README-zh.md)

我们曾尝试在同一个 Session 内保留旧节点, 通过新增节点支持历史编辑和分支切换. 放弃这个设计的主要原因是执行归属变得过于复杂, 而不是最近公共祖先(LCA)查询的性能.

## 为什么保留旧节点还不够

历史并不只有已经保存的消息. 一个分支里可能启动了尚未结束的子代理. 用户切换分支后, 后台工作仍然可能完成并产生结果.

例如在分支一启动子代理, 随后切到分支二, 就必须决定该结果是否可以进入当前对话. 即使明确禁止交付给分支二, 也需要判断它属于哪个 Turn, 这个 Turn 从哪里分叉, 以及它与当前历史是什么关系.

原本清楚的 Session, Turn 和 Message ID 对应关系, 因而还要叠加分支关系, 继承范围与派生工作的交付规则. 新增节点并保留旧节点, 不会自动解决这些问题.

## 为什么 LCA 不能替我们作决定

最近公共祖先 LCA 可以帮助找到两个节点共同的历史位置. 它回答节点之间的关系, 不能决定一个旧分支的子代理结果是否应该出现在另一个分支里.

我们不愿意仅为了保留历史分支, 就持续增加这套业务判断. 即使树查询足够快, 仍然需要让每项派生工作的归属和可见范围说得清楚, 并处理分支切换时尚未结束的执行.

## 目前保留的选择

我们选择暂时取消 Session 内的历史分支编辑与切换, 保留明确的 Session, Turn 和 Message 对应关系. 当前的 fork 是复制历史并创建另一个 Session, 后续执行在各自的会话中保存, 不在原 Session 内来回切换当前分支.

代价是用户无法在同一 Session 中任意选择旧分支继续对话, 也不能用这套旧设计修改某个 Turn 后保留全部后续分支. 我们接受这个功能范围, 等用户明确需要时再重新评估.

重新考虑时, 要先明确后台结果, 派生任务和历史可见性如何归属, 再决定是否需要树结构或怎样查询共同祖先. 当前 fork 的具体资源和历史规则见 [Session 模块](../../../src/session/README-zh.md).
