# 为什么由 Node 直接写限长的 JSONL 诊断文件

[English](README.md) | [文档入口](../../README-zh.md)

Server 和 `src/` 下的业务包都运行在 Node 进程中. 诊断记录产生在模型报错, HTTP 失败, MCP 会话和 Turn 状态切换现场, 因此需要决定是把日志打印给 Rust 宿主转发保存, 还是由 Node 自己持久化结构化文件.

## 为什么不经 Rust 宿主转发保存

另一种方案是让 Node 把日志输出到 stdout/stderr, 由 Tauri 的 Rust 宿主初始化原生日志器, 解析这些文本, 管理文件轮换, 并在退出时协调刷盘.

这条边界会带来两个现实问题:

- 脱离桌面宿主运行的 Server 场景 (自动化测试, `--server-only` 发布自检以及单独启动 Server) 会与桌面启动路径产生两套不同的日志落盘行为.
- 所有结构化错误, ID 和脱敏后的 `body` 都要先序列化进子进程标准输出, 再由 Rust 解析并额外维护一套关闭前等待接口, 才能避免宿主提前强杀进程丢失末尾日志.

因此我们选择由 Node 通过 [Logging](../../../src/logging/README-zh.md) 直接把诊断文件写入 `<Profile>/logs`, 让 Rust 侧只从 stdout 读取 `server.ready` 启动通知. Rust 不初始化日志器, 不构造业务日志记录, 也不管理日志文件.

## 为什么限制单条体积并在拥堵时计数丢弃

诊断日志不能反过来拖垮内存占用, 也不能在磁盘卡顿或调用方高频报错时阻塞对话主链路:

- **单条 8 KiB 上限**: `message`, `error` 和 `body` 共用单行 8 KiB 预算. 超大单值在脱敏前整体省略, 避免截断留下半截凭据; 对 `body` 也不触发普通 getter 或自定义 `toJSON`.
- **64 KiB 写入缓冲阈值**: `FileLogWriter` 在达到 64 KiB 缓冲阈值或上一份轮换文件仍在关闭时, 对新日志只递增丢弃计数并放弃正文, 不在内存中无限堆积发送队列. 恢复写入或关闭时通过 `logging.dropped` 报告丢弃数量.
- **容忍并发清理**: 单文件 10 MiB 轮换和 14 天 / 100 MiB 清理会避开其他存活进程的日志, 并在另一进程先一步删掉旧文件时扣除已统计大小, 避免误报容量不足而永久停写.

## 接受的成本与局限

- **拥堵丢弃的正文无法补回**: 阻塞期间只保留丢弃条数, 不能还原原日志内容; 可恢复交付仍是 [fileWriter.ts](../../../src/logging/fileWriter.ts) 中的未完成项.
- **限时关闭 (`2000 ms`)**: `closeLogging(timeoutMs = 2000)` 在业务收尾后停止接收并等待已接受写入, fsync 与文件关闭, 超时或失败返回 `false`. 卡在系统 I/O 上的句柄还不能独立重启, 强杀进程或断电仍可能丢失尚在缓冲中的尾部记录.
- **不集中登记业务事件表**: 各模块直接选择 `target` 和 `event` 标识, 调用方需避免把用户文本或凭据写进这两个固定字段, 修改字段时对照 [Logging 模块](../../../src/logging/README-zh.md) 约定核对.
