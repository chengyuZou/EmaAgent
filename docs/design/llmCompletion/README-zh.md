# 为什么 Complete 在内部收集流式结果

[English](README.md) | [文档入口](../../README-zh.md)

摘要, 提词等调用只需要等待完整结果, 不需要逐段展示. 但调用方想一次拿到结果, 不代表底层请求必须使用非流式传输.

## 为什么没有继续使用原生非流式请求

手动压缩曾遇到下面的实际错误:

```text
Streaming is required for operations that may take longer than 10 minutes.
```

当时完整结果调用使用非流式请求. Anthropic SDK 会根据输出预算等条件检查非流式请求是否被允许, 因而可能在发送 HTTP 前就拒绝请求. 这条错误不表示模型已经运行了十分钟, 也不能仅凭它认定为网络慢或摘要内容有问题.

如果继续直接使用非流式接口, 这类只想等待最终结果的业务也需要分别应对传输方式的限制. 单纯降低输出预算又可能限制任务实际需要的结果长度.

我们选择保留完整结果的使用方式, 在 Complete 内部使用 CallLLM 的流式请求, 收集完毕再返回. 主要原因是处理这次实际暴露的请求限制, 而不是认为聚合流天然更快.

## 为什么调用方不传入 CallLLM

Complete 工厂内部创建 CallLLM, 调用方只提供连接, 模型和请求. 调用一次 Complete 对应一次模型请求, 不需要先请求一遍流式结果, 再补发一遍完整结果请求.

这样摘要和提词等调用方不必了解如何拼接增量, 保持内容块顺序, 收集用量或关闭流. 同一套请求转换和流事件处理也不必为非流式接口再维护一份.

每次请求独占自己的流和收集内容, 工厂可以复用 SDK Client. 这些生命周期由调用实现处理, 不要求每个使用者再管理一份 CallLLM.

## 接受什么成本和限制

完整结果需要在内存中收集. 调用方仍然等到收集完成才获得结果, 不能因为底层是流式就认为业务会提前完成或内存占用更低.

流式请求仍然可能超时, 断开, 被限流或被取消. 失败不会伪装成成功的完整结果, 也不会为了补齐结果自动重新发起模型请求. 正常触及输出上限时, 调用方仍需根据结束原因判断是否可以使用结果; 完整响应不等于回答已经完成了全部任务.

当前选择解决的是传输方式与结果使用方式不必绑定的问题. 具体转换和错误约定见 [LLM 模块](../../../src/llm/README-zh.md), 工厂实现见 [languageModel.ts](../../../src/llm/languageModel.ts).
